# CloudPath Analyzer — 1차 출시 범위 및 완료 기준

- 작성일: 2026-11-25
- 상태: 1차 개발 범위 개정안 (기능 구현 완료 선언이 아님)
- 적용 기준: Phase 6-1-4 이후 개발 계획
- 상위 비전: 기존 PROJECT_VISION.md의 범용·하이브리드 인프라 분석 목표를 유지한다.
- 범위 우선순위: 이 문서는 1차 출시 범위와 완료 판정에 한해 기존 로드맵을 보완한다. 기존 설계의 기술적 원칙이나 장기 목표를 폐기하지 않는다.

## 1. 목표

AWS 인프라를 배포 전과 배포 후 모두 분석하고, 구조·정책·예상 전달 경로 및 장애 원인을 웹에서 안정적으로 확인할 수 있는 독립적인 분석 서비스를 1차 출시(V1)의 목표로 한다. IaC 검증과 실제 구성 분석은 동일한 공통 데이터 모델을 사용하되 입력의 출처 및 확실성을 구분한다. 시각적 편집은 1차 출시의 필수 기능이다. 일정이나 테스트 개수만으로 완료를 선언하지 않는다.

## 2. AWS 인프라 종합 분석의 범위

‘AWS 전체 분석’은 모든 AWS 서비스와 기능을 무조건 지원한다는 의미가 아니다. 지원 범위를 명시한 AWS 네트워크 중심 종합 분석을 의미하며, 아래의 V1 필수 범위 및 종단 간 시나리오를 검증해야 한다. 개별 서비스에서 미지원 속성이나 연결은 UNKNOWN 또는 지원 범위 외로 표시한다. 전체 서비스 카탈로그에 대한 완전한 지원은 장기 확장 과제로 남긴다.

| 영역 | V1 필수 개발 목표 (완료 여부와 별개) |
|---|---|
| 입력 | 복수 Terraform HCL, Plan JSON, AWS 읽기 전용 Inventory. 변수·Module·반복 생성 및 미확정 관계에 대한 명시적 처리 |
| 기본 네트워크 | VPC, Subnet, EC2, ENI, SG, NACL, Route Table, IGW, NAT Gateway; 기본/명시적 연결, 경로 우선순위, blackhole, NAT 변환 |
| 연결 확장 | VPC Peering, Transit Gateway, VPC Endpoint(Interface/Gateway), 다중 VPC 경로. 계정·Region 경계 및 수집 누락을 명시 |
| 서비스 경로 | ALB/NLB Listener·Target Group, ECS/Fargate, RDS, EKS의 VPC/노드/ENI 수준 연결, S3 접근 경로. EKS Pod 내부 및 서비스 메시 등은 별도 지원 명세 필요 |
| 접근 제어 | 네트워크 정책과 IAM/리소스 정책을 분리. 지원되는 API 접근 조건과 관련 정책을 평가하고 미지원 조건·SCP·세션 정책 등 확인 불가 영역은 UNKNOWN |
| 진단 | 요청/응답, 최초 차단, 후속 조건부 차단, 자연어 규칙 근거, 구조도 강조 및 원본 증거 |
| AWS 도구 연계 | Reachability Analyzer 결과(정적 검증)와 Flow Logs(관측) 가져오기 및 비교. 별도 명시적 동의 없이 유료 분석 실행 또는 리소스 변경 금지 |

IPv4를 우선 검증하되 IPv6, 다중 계정/Region, 복합 하이브리드 연결은 실제 지원 수준을 별도 매트릭스에 기록한다. 미검증 경로를 지원 완료로 주장하지 않는다. DNS, TLS, OS 방화벽, 애플리케이션 동작 등은 별도 증거 없이는 통신 성공으로 확정하지 않는다.

## 3. 웹 시각화 및 구조도 편집 요구사항

- Network Topology: VPC/Subnet 소속 경계, 정책 적용 관계, 경로 대상, Packet Trace 강조를 구분한다. IaC References는 코드 의존성을 표현한다.
- 편집 모드: 리소스 박스 드래그, 소속 영역 내부 이동, 경계 밖 정책의 배치 제약, 연결선 재계산 및 장애물 회피를 제공한다. 이동은 시각적 좌표만 변경하며 실제 리소스의 소속·정책·분석 결과를 변경하지 않는다.
- 접기/펼치기: VPC/Subnet 단위로 내부 노드를 요약한다. 접힌 그룹의 외부 연결은 요약하고 내부 차단/미확정 개수 및 상태를 표시한다. 원래 경로의 의미나 차단 지점을 숨기지 않는다. 접기/펼치기에 따라 분석 결과가 바뀌지 않는다.
- 배치 저장: 입력 지문 및 그래프 모드별로 사용자 배치를 저장·복원하고 자동 배치로 초기화할 수 있어야 한다. 입력 변경 시 삭제된 리소스나 잘못된 소속의 좌표를 재사용하지 않는다. 초기 구현은 로컬/브라우저 저장을 기본으로 하고 민감한 구성 자체는 불필요하게 저장하지 않는다.
- 가독성: 확대/축소, 이동, 빈 영역 제거, 정책 계층 토글, 확대율과 독립적인 리소스 팝업, 차단 진단 팝업 및 상세 원본 JSON을 유지한다.
- 성능: 대형 입력에서 브라우저가 멈추지 않도록 제한·취소·오류 표시 또는 단계적 렌더링을 제공한다. 표시하지 못한 선 또는 겹침을 숨기지 않는다.

## 4. 판정 정확성 원칙

- 공통 모델에서 소속, 정책 적용, 전달, IaC 의존성을 분리한다. Forwarding과 Policy Evaluation을 분리하고 요청/응답을 평가한다.
- HCL/Plan 예상 판정, AWS 수집 구성의 정적 판정, Reachability Analyzer의 정적 결과, Flow Logs의 실제 관측을 구별한다. 수집 시각·범위·제약 및 입력 지문을 표시한다.
- 확정되지 않은 ID, 다중 후보, 누락된 규칙, 지원하지 않는 기능은 임의의 연결이나 PASS로 변환하지 않는다. 조건부 후속 결과는 최초 차단의 실제 도달 여부와 구별한다.
- AWS 설정이 허용하는 경로와 실제 애플리케이션 응답은 동일하지 않다. 분석은 읽기 전용이며 자동으로 배포하거나 정책을 수정하지 않는다.

## 5. 안정적인 웹 서비스 제공

- 설치/기동/재기동/분석/초기화 절차 및 오류 복구 문서화. 입력 검증, 일관된 오류 응답, 분석 시간 제한, 요청 제한, 실패 시 이전 정상 구성 보존, 동시 요청 및 오래된 입력 지문 처리.
- 데이터 및 자격증명 보호: AWS 인증은 수집 경로에만 사용, 최소 조회 권한, 입력/로그/결과의 민감 정보 최소화, 비밀값 저장·공개 금지, 파일 크기 및 구조 제한, 안전한 출력 인코딩.
- V1 운영은 필요할 때 로컬에서 기동·종료하는 단일 사용자 도구로 확정한다. 기본 loopback 바인딩 및 로컬 보안 검수는 필수다. 외부 또는 다중 사용자 공개가 목표라면 인증·인가, TLS, 세션/테넌트 격리, 비밀 관리, 운영 모니터링, 보관/삭제 정책을 출시 필수 조건으로 추가한다. 개발용 로컬 서버를 그대로 공개하지 않는다.
- 상태 확인, 재현 가능한 테스트, 설치/실행 가이드, 버전 및 지원 범위 문서를 제공한다. 운영 환경, 부하 규모, 응답시간 목표는 별도 측정 후 확정한다.

- [ ] 대표 소규모/복합/대형 샘플의 성능 측정과 합의된 목표 충족. 목표 및 측정 환경을 별도 기록.

## 9. V1 사용자 이용 흐름 및 통합 검수 보강 (2026-11-28)

사용자와 확인한 핵심 결과물은 웹 서비스에서 Terraform 파일을 전달하고, 구조도를 구성한 뒤, Packet Trace 화면에서 필요한 가상 통신 테스트를 사용자가 선택하여 실행하는 것이다. 실제 AWS Inventory 분석은 별도의 보완 입력 모드이며, 이 흐름을 대체하지 않는다. V1의 기존 필수 범위와 완료 조건은 유지한다.

### 추가 통합 요구사항

- 복수 Terraform 파일을 웹에서 업로드하고, 입력 오류/미확정 변수/Module/반복 생성의 처리 근거 및 부분 분석 한계를 표시한다. 필요한 값은 명시적 입력이나 지원되는 Plan JSON으로 보완한다. 배포, Terraform 자동 실행, 실제 패킷 송신은 하지 않는다.
- HCL 예상 구성, Plan 예상 구성, AWS Inventory 관측 구성 및 Kubernetes/ECS 추가 증거를 공통 모델에 연결하되 데이터 출처·확실성·입력 지문을 보존한다. AWS 스냅샷용 엔진에서 사용한 실제 ID/ENI/Pod IP/Health 등을 미배포 Terraform에 임의로 만들어 실제 관측으로 표시하지 않는다. 미확정 주소는 명시적 가정 또는 UNKNOWN으로 처리한다.
- 통합 구조도에서 계층·소속·정책·논리 Service·전달 경로를 구분하고, 출발지/목적지/프로토콜/포트를 지정한 요청 및 응답 검사, 후보 분기, 최초 차단 위치, 독립 후속 검사와 원본 근거를 일관되게 표시한다. 별도 CLI/진단 페이지의 존재만으로 V1 통합 완료를 선언하지 않는다.
- Terraform 대표 복합 예제에서 VPC/Subnet/EC2/SG/NACL/Route/NAT 및 지원 범위의 ELB, ECS, EKS, RDS, Endpoint, 다중 VPC 등을 실제 AWS 배포 없이 검수한다. Kubernetes 리소스/런타임 정보가 Terraform에 없으면 필요한 추가 입력과 미확정 범위를 명시한다. IaC 지원 매트릭스를 AWS 스냅샷 지원 매트릭스와 별도로 관리한다.
- 동일 시나리오를 HCL/Plan/실제 AWS 구성 및 관측 증거로 비교할 수 있는 경우 차이를 기록한다. 동일한 분석 규칙의 재사용은 입력 모드별 전제와 충분한 데이터가 있을 때만 허용한다.
- 7-D5c(조건부 Service DNAT 및 Backend 검사), 7-D5d(CNI 실제 적용 증거), 7-D5e(ELB-to-ECS Task 경로)를 7-D6 웹 통합 이전 보완 대상으로 둔다. 실제 AWS 검증은 Phase 8 필수 출시 게이트로 유지한다.
- 웹 UI는 로컬 단일 사용자 환경에서 제공한다. 향후 외부 공개/다중 사용자로 확장한다면 기존 5절의 인증·TLS·테넌트 격리·민감 데이터 보호·운영 보안 요건을 필수로 적용한다.

## 10. 로컬 운영 결정 및 기술 부채 관리 (2026-11-28)

V1.0은 필요할 때 로컬에서 실행하는 단일 사용자 웹 기반 분석 프로그램이다. 브라우저에서 Terraform 파일을 업로드하고 구조도 및 가상 Packet Trace를 이용한다. 공개 배포는 V1 필수 조건이 아니며 별도 보안 게이트로 관리한다. 기본 loopback, 기동·종료·재기동, 입력·출력 검증, 민감정보 보호, 실행 자원 제한, 읽기 전용 보장과 실제 AWS 교차 검증은 V1 필수다.

`docs/CLOUDPATH_TECHNICAL_DEBT.md`를 출시 게이트 관리 대장으로 사용한다. 공통 SG 참조 → ELB-to-task → 동일 subnet/node 및 주소 변환 보완 → 컨테이너 웹 → 관리형 서비스 → Terraform/AWS 통합 → 실제 AWS·브라우저·로컬 안정화 검수 순서를 따른다. 공개 운영은 별도 승인 후 진행하며 기존 V1 핵심 사용자 흐름 및 완료 판정을 축소하지 않는다.

## 11. V1 로컬 컨테이너 배포 (2026-11-28)

V1 기본 배포 형태는 Docker 이미지이며, 사용자가 필요 시 자신의 PC에서 컨테이너를 시작하고 브라우저에서 로컬 웹 UI를 이용한다. Docker Hub에는 프로그램 이미지만 배포하며, 사용자의 Terraform, AWS 스냅샷, 자격증명, 분석 결과는 이미지나 원격 서비스로 전송하지 않는다. 기본 실행 예시는 host `127.0.0.1:8000`에만 포트를 publish하고 컨테이너 내부 listener는 `0.0.0.0:8000`으로 제한된 컨테이너 프로파일에서 동작하도록 구성한다. Native 로컬 기동 기본 loopback은 유지한다. Docker 버전과 로컬 포트 격리 실제 검수 필요.

- 8-D: Dockerfile, compose.yaml, .dockerignore, 고정 의존성, non-root, 최소 권한, no privileged / Docker socket / host network, CPU·memory 제한, 선택적 로컬 데이터 volume, 비밀정보 없는 build context, 이미지 취약점 검사 및 버전 태그. Terraform 입력은 실행하지 않으며 클라우드 수집은 명시적인 read-only 사용만 허용한다.
- 8-E: 깨끗한 지원 호스트에서 image pull/build, loopback 접속 및 외부 비노출, Terraform 업로드→Topology→Packet Trace E2E, 중지·재시작·삭제·버전 변경, 데이터 보존/삭제, AWS 읽기 전용 수집 프로파일, 이미지 태그/digest 확인. GitHub Release와 Docker Hub 배포는 위 검수 및 기존 V1 게이트를 통과한 후 진행한다.
- [ ] 로컬 컨테이너 기본 프로파일 및 Docker Hub 이미지 배포 검수 (CP-DEBT-015).

공개 이미지 배포와 공개 웹 서비스 운영은 별개의 범위다. 공개/다중 사용자 서비스 운영은 별도 승인과 보안 게이트를 유지한다.

## 사용자 진단 설명 게이트 (CP-DEBT-016)

V1 모든 분석 화면에서 최초 정적 차단 또는 미확정 위치, 원인과 관련 증거, 추가 독립 검사 및 조건부 응답을 자연어로 설명한다. 실제 성능 병목·현재 세션 성공은 근거 없이 추정하지 않는다. 미지원 사유를 명시하고 원본 코드/JSON을 보존한다. 외부 AI API 없이 로컬에서 재현 가능해야 하며, 8-B에서 전체 화면 검수한다.

## V1 기술 부채 집중 상환 순서

관리형 서비스 7-E~G 이후 7-H1 공통 정책·전달 예외, 7-H2 Terraform/Plan 해석, 7-H3 공통 모델/연속 경로, 7-H4 통합 웹/자연어 진단 순으로 상환한다. 8-A~E의 실제 AWS 수집/교차검증, 브라우저 E2E, 로컬 안정성·보안·성능, Docker 패키징·독립 실행 검수는 필수 게이트 유지. V1 지원 범위 축소는 별도 승인 필요.

### IAM 입력 및 변경 시뮬레이션 보강 (2026-11-28)

IAM 구성은 실제 AWS 읽기 전용 수집(OBSERVED), Terraform 배포 예정(PLANNED), 웹 수동 등록(HYPOTHETICAL)을 공통 정규화 모델로 표현한다. 선택한 원본과 별도의 가상 변경만을 결합해 EFFECTIVE 시나리오를 구성하고, 원본·출처·계정·시각·불완전성을 유지한다. 웹 IAM 관리 화면은 주체/정책/연결 관계의 조회·등록·가상 편집·변경 전후 비교와 명시적 내보내기를 지원한다. 실제 AWS 변경 API나 웹 자격 증명 입력/저장은 금지하고, 실제 수집은 사용자 요청에 의한 읽기 전용 프로파일로 제한한다. G3a.1은 정규화 등록 계약 및 오프라인 시나리오 기반만 구현하며 7-G3a.2~G5, 7-H2, 8-A 및 기존 모든 출시 검수 조건을 유지한다.
